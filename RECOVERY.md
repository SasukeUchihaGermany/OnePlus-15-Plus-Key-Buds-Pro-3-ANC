# Reinstall and recovery guide for an AI agent

Follow [SETUP.md](SETUP.md) for the complete ordered installation, Developer options, Shizuku pairing/authorization and reboot setup. This document adds build and agent-specific recovery context. For a full removal and security/debugging reset, use [UNINSTALL.md](UNINSTALL.md).

Read AGENTS.md, README.md and VALIDATION.md first. Target tested: OnePlus 15 CPH2747, Android 16, OxygenOS CPH2747_16.0.9.400(EX01), OnePlus Buds Pro 3. Do not assume another firmware has the same input node or privileged APIs.

## Restore the controller

1. Install Android SDK platform-tools, platform android-36 and build-tools 36.1.0, and JDK 17 or newer. Android Studio can supply these. This project uses PowerShell and direct javac/d8/aapt2; Gradle is unnecessary. All four pinned Shizuku API jars and their MIT license are in libs/.
2. Prefer the bundled signed BudsAncLab.apk for a reinstall. For a source build, run `./test.ps1 -Jdk 'C:\path\to\jdk'`, then `./build.ps1 -Jdk 'C:\path\to\jdk' -Sdk 'C:\path\to\Android\Sdk'`. Build intermediates use .build/ and the development signing key uses .local/local.p12; both are ignored. Keep the original local key privately for compatible updates. A new key cannot update an existing differently signed installation; an intentional uninstall/reinstall loses app settings and grants. Do not uninstall silently to resolve a signature error.
3. Enable Developer options and USB debugging, connect/unlock the phone, and accept the PC authorization. Use `adb devices` to verify. Do not export serials, addresses, ADB keys or pairing codes to the repository.
4. Run `adb install -r ./BudsAncLab.apk`, then `adb shell am start -n dev.local.anc/.MainActivity`. Grant Nearby devices and notifications in the phone UI. This firmware originally rejected shell runtime grants, so use the UI rather than repeating denied commands.
5. Install Shizuku from its [official project](https://github.com/RikkaApps/Shizuku/releases) if missing. The tested manager was 13.6.0.r1086.2650830c. Start via Wireless debugging: open Shizuku's pairing tutorial, open Developer options > Wireless debugging > Pair device with pairing code, then enter that code in Shizuku's pairing notification. Pair Shizuku's own on-phone key; PC pairing alone does not supply that key. Never collect or commit its private key. Return to Shizuku and use Start under Wireless debugging. Verify running before continuing.
6. On this tested OxygenOS build Shizuku authorization required Developer options > **Disable system optimisation** ON (older guides call it Disable permission monitoring). The owner explicitly approved this OEM-wide setting in the original setup. Its warning covers security, power, system and display effects; explain that scope before applying it on a new device. Confirmed property: `adb shell getprop persist.sys.permission.enable` returns false. After changing it, restart Shizuku so its process receives the changed permissions.
7. In Plus Key ANC, tap ENABLE KEY, allow Shizuku, then START. Wear both earbuds and connect through normal Bluetooth. The app captures the dedicated key only while the exact paired Buds Pro 3 is A2DP-connected. The existing native key assignment can remain Translate. Tasker is unnecessary.
8. For background reliability, exempt both apps through their battery settings, or use `adb shell cmd deviceidle whitelist +dev.local.anc` and `adb shell cmd deviceidle whitelist +moe.shizuku.privileged.api`. Enable any OxygenOS app auto-launch allowance exposed for them. Do not claim a setting was applied without checking it.

## Reboot startup and debugging requirements

The app stores START/STOP in private preferences and receives BOOT_COMPLETED. START_STICKY provides process restart; it does not undo an explicit Android force-stop. Open and START after force-stop or reinstall.

Reliable physical key capture here requires Shizuku shell privileges. The temporary accessibility probe did not receive scan code 735; the OEM observer API rejected the app for missing signature-only `oplus.permission.OPLUS_COMPONENT_SAFE`. No verified debugging-free rootless replacement was found. Do not propose root, bootloader unlocking or platform signing as routine recovery.

The tested Shizuku manager contains an Android 13+ ADB boot path. Requirements: its own wireless pairing remains valid, last launch mode is ADB, WRITE_SECURE_SETTINGS is granted, Wi-Fi/debugging is available, and the manager can receive boot broadcasts. The installed manager already had WRITE_SECURE_SETTINGS. Check `adb shell dumpsys package moe.shizuku.privileged.api` locally for that specific grant; avoid saving the whole dump. If a fresh install lacks it, grant only with the owner's authorization using `adb shell pm grant moe.shizuku.privileged.api android.permission.WRITE_SECURE_SETTINGS`; OEM restrictions may require the setting above.

That boot path enables both USB and wireless ADB and sets `adb_allowed_connection_time=0` (authorization does not expire). The owner authorized these effects for this setup after asking for a debugging-free alternative. Keep them explicit in recovery instructions. There is no PC or Internet requirement once configured, but this is not operation with debugging disabled. Its discovery window is only three seconds, so boot Wi-Fi timing can affect success. Validate a real reboot with USB disconnected and no manual Shizuku start; see VALIDATION.md for the actual result, rather than assuming source code proves success.

Upstream boot implementation inspected at commit b844bc491f1790c72328e1a8e5b2349f8978f0ea: https://github.com/RikkaApps/Shizuku/blob/b844bc491f1790c72328e1a8e5b2349f8978f0ea/manager/src/main/java/moe/shizuku/manager/receiver/BootCompleteReceiver.kt . The installed APK's receiver was independently inspected and has the same conditions/settings behavior.

If auto-start fails, open Shizuku and use Wireless debugging Start, then open Plus Key ANC and START. Do not describe this fallback as unattended recovery. To disable auto-start privilege, revoke WRITE_SECURE_SETTINGS from Shizuku and turn debugging off in Developer options; this also prevents automatic key capture recovery. To undo battery exemptions, replace + with - in the whitelist commands. Turn Disable system optimisation OFF to restore the OEM protection, accepting that key capture may stop working.

## Verify and diagnose

Use only targeted logs: `adb logcat -d -v time -s BudsAncLab:I`, and `adb shell am broadcast -n dev.local.anc/.DiagnosticReceiver --es command QUERY`. Never export general phone logs or unrelated notification contents. Check for one dev.local.anc:pluskey helper process and CAPTURE ON (Shizuku). STOP should release capture and exit the helper. On app version changes, increment manifest versionCode; the Shizuku service version derives from it. Destruction uses Shizuku's USER_SERVICE_TRANSACTION_destroy constant.

Test single three times (High, Medium, Low cycle), double (Auto), hold (Transparency/Off), locked operation, external earbud mode change then single, music continuity and reboot without USB. Verify actual-mode replies, not just successful socket writes. Preserve honest outstanding tests in VALIDATION.md. Before wear detection was satisfied commands returned rejection 0x0E. If native Earbud functions holds the vendor RFCOMM connection, close its page and retry START; the app does not force-stop it automatically. Never reset/unpair the earbuds to work around this.
